# TDD Guard Test Quality Rules

**Source:** `~/formaltask/.claude/tdd-guard/data/instructions.md`

This file contains the comprehensive 478-line AI validation ruleset used by tdd-guard to validate test quality.

## Purpose

Defines natural language rules for AI-powered test quality validation. Claude Sonnet 4 validates tests against these criteria before allowing Write/Edit operations.

## Location

The canonical version lives at:
```
~/.claude/tdd-guard/data/instructions.md
```

## Usage

When tdd-guard PreToolUse hook fires:
1. Reads test.json (generated by pytest/jest/BATS)
2. Checks if tests cover modified files
3. Sends test code + instructions.md to Claude API
4. Claude validates against rules and returns violations
5. Blocks operation if critical violations found

## Key Sections

### Core Test Quality Requirements

1. **Assertions Required** (lines 10-37)
   - Every test MUST have at least one assertion
   - Assertions MUST have descriptive failure messages
   - Example: `assert result == expected, "Detailed explanation of what failed"`

2. **Test Naming Conventions** (lines 39-62)
   - Format: `test_<component>_<scenario>_<expected_outcome>`
   - Good: `test_login_invalid_password_returns_401()`
   - Bad: `test_user_login()` (too vague)

3. **Test Independence** (lines 64-99)
   - Tests MUST NOT depend on execution order
   - Each test sets up its own state
   - No shared mutable state between tests

4. **Determinism Requirements** (lines 101-135)
   - NO random data without fixed seeds
   - NO real timestamps (mock time/date functions)
   - NO network calls (mock external APIs)
   - NO file system operations on real paths (use temp directories)

5. **Behavioral Testing** (lines 137-172)
   - Test public interfaces, not private methods
   - Verify inputs, outputs, side effects
   - Don't assert on internal state
   - Don't test implementation details

### Project-Specific Rules

1. **MCP Server Tests** (lines 176-214)
   - Test all API endpoints (success AND error cases)
   - Test all HTTP status codes (200, 400, 401, 404, 500)
   - Test request validation (missing fields, invalid types)
   - Use test database fixtures with automatic rollback
   - Mock all external API calls

2. **Hook Tests** (lines 216-253)
   - Integration tests in `hooks/tests/` directory
   - Test success and failure scenarios
   - Verify correct exit codes (0 for success, non-zero for errors)
   - Verify output messages to stdout/stderr
   - Test with realistic file system state

3. **Claude Code Integration Tests** (lines 255-264)
   - Mock Claude API calls (never real API requests)
   - Test command parsing and validation independently
   - Use temporary directories for file operations
   - Verify configuration loading and validation
   - Test error messages and user-facing output

### Anti-Patterns to Avoid

1. **The Mockery** (excessive mocking) (lines 267-306)
   - Limit mocks to external dependencies only
   - Use real internal collaborators (validators, hashers, loggers)
   - Don't test mock interactions, test real behavior

2. **The Giant** (tests >20 lines) (lines 308-344)
   - Split large tests into focused, single-behavior tests
   - Use fixtures for complex setup
   - One assertion per logical concept

3. **Excessive Setup** (>5 lines) (lines 346-396)
   - Extract setup into pytest fixtures or helper functions
   - Setup should be clear and minimal
   - If setup is complex, test is probably testing too much

4. **The Liar** (misleading test names) (lines 398-420)
   - Test name MUST describe behavior being verified
   - Don't claim to test X but actually test Y
   - Name should indicate what failed when test breaks

5. **The Inspector** (testing private methods) (lines 422-450)
   - Only test public interfaces
   - Private methods are implementation details
   - Refactoring should not break tests

### Validation Approach

**7-Step Checklist** (lines 451-478):

1. Does test have at least one assertion?
2. Is test name descriptive and follows convention?
3. Is test independent (no execution order dependency)?
4. Is test deterministic (no random data, timestamps, network)?
5. Does test verify behavior, not implementation?
6. Are there any anti-patterns present?
7. Does test follow project-specific requirements?

**Error Reporting Format:**
```
❌ Violation: [Anti-Pattern Name]
Location: tests/test_file.py:42
Issue: [Specific problem description]
Fix: [Actionable remedy]
Severity: [blocking|warning|suggestion]
```

**Starting Philosophy:**
- Permissive → Strict (gradual enforcement)
- Warnings first, then blocking
- Educate developers through clear error messages
- Build test quality culture over time

## Cost

~500 tokens per validation (~$0.003-0.006 per Write/Edit operation with Claude Sonnet 4)

## Customization

To add project-specific rules:

1. Edit `~/.claude/tdd-guard/data/instructions.md`
2. Add new section under "Project-Specific Rules"
3. Include examples of violations and correct patterns
4. Specify severity (blocking vs. warning)
5. Test with sample code to verify AI understands rules
